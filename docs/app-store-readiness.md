## Implemented

- Native Sign in with Apple uses Apple's button, a hashed nonce, state verification and Supabase identity verification. Name is only an optional profile default; legal-age confirmation remains required. A backend readiness check runs before the Apple sheet, so an unconfigured server cannot begin new Apple sign-ins.
- The one-use Apple authorization code is exchanged server-side. The returned identity is verified against Apple's signed JWKS, issuer, audience and the user's trusted Supabase Apple subject. A refresh token is stored as an authenticated AES-256-GCM JWE bound to the account; no raw provider token is placed in app storage or logs. Capture uses the initiating session token across account changes.
- Account deletion revokes Apple authorization before Storage/Auth cleanup, records a claim-bound acknowledgement and safely retries failures. SQL rejects deletion completion without revocation. An Apple account missing a captured grant gets an in-app reconnect action before scheduling. Email-only accounts need no Apple step. At pre-deployment audit there were zero hosted Apple identities, so no legacy grant required backfill.
- Personal entries/plans/photos are erased. Authored shared-night titles and shared-bottle labels become generic; the other participants keep their own records. See [deletion operations](account-deletion-and-photo-limits.md).
- Native policies work offline; public privacy, terms, support and deletion resources use the current owner-supplied contact. The shared privacy policy describes provider-token revocation.
- Production/testing iOS configurations enforce App Transport Security. HTTP access is limited to development builds. Unused Face ID and always/background location permission strings are removed; location and photo purpose strings explain the actual use.
- `ios.privacyManifests` declares no tracking, account-linked app data and reasons for UserDefaults, file timestamps and disk space. Expo/React Native SDK manifests remain included. Native config declares exempt encryption for standard HTTPS/OS storage; review that declaration if cryptography changes.
- Notification opt-in copy explicitly includes weekend/holiday planning messages and explains the planning-category opt-out. Notifications/location are optional. Report/block and photo-approval controls from the Google Play pass apply on iOS too.
- Ten missing foreign-key indexes identified by hosted advisors are added for account/notification cleanup.

## Configure Apple before TestFlight

1. Confirm bundle `com.dwd.app` and EAS project in `apps/mobile` match App Store Connect. Register that App ID with Sign in with Apple and configure its capability. Configure Supabase Apple Auth with the native bundle identifier. Native ID-token login does not require a web Services ID; adding browser Apple OAuth later requires its own callback/client-secret setup and rotation. See [Supabase Apple Auth](https://supabase.com/docs/guides/auth/social-login/auth-apple).
2. Create a Sign in with Apple key in the matching Apple Developer team. Keep its `.p8` private key server-only. Set these **Supabase Edge secrets**, using an ignored local env file and the CLI's `secrets set --env-file` command: `DWD_APPLE_TEAM_ID`, `DWD_APPLE_KEY_ID`, `DWD_APPLE_CLIENT_ID=com.dwd.app`, `DWD_APPLE_PRIVATE_KEY`, and `DWD_APPLE_TOKEN_ENCRYPTION_KEY`. Team/key IDs are ten uppercase letters/digits; the encryption key must be 32 cryptographically random bytes expressed as 64 hex characters. PEM can contain actual newlines or literal `\n` escapes. Do not put the private key/encryption key in `EXPO_PUBLIC_*`, app config, source control or chat.
3. Keep the token-encryption key backed up securely. Changing it without re-encrypting stored credentials makes them unreadable and blocks Apple deletion jobs. Client ID/private key/team must correspond to each captured grant. Private token tables have no client/service table-read grants; only the service RPCs used by Edge Functions may access them.
4. Deploy `apple-account-token` and `delete-accounts` after the migration. Both use `verify_jwt=false`: POST capture verifies the actual Supabase user; deletion uses the existing scheduler secret; GET capture exposes readiness only. A readiness HTTP 503 means missing/invalid Apple secret configuration, not a successful Apple rollout. Never enable the store Apple login flow until readiness returns 200 and real Apple exchange/revocation is tested.
5. Configure Apple signing, APNs, production EAS environment and `DWD_APPLE_TEAM_ID` for associated domains. Private keys above stay only in Supabase; EAS needs its signing credentials separately. Configure a working SMTP sender and register it for Apple's private email relay if sending to relay addresses.
