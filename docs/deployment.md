### Exact update workflow

Run from the repository root:

```sh
git switch main
git pull --ff-only origin main
git switch -c feat/your-change
# Make changes.
npm ci
npm run typecheck
npm run lint
npm run format:check
npm test
npm run build
git add <the-files-you-changed>
git diff --cached
git commit -m "Describe the resulting behavior"
git push -u origin feat/your-change
```

Open a pull request from the feature branch to `main`, check its Vercel Preview, and review the diff and Checks results. If it contains SQL, complete the separate migration release below before merging code that requires it. Merge the pull request on GitHub; Vercel deploys `main` automatically. Then update the local checkout:

```sh
git switch main
git pull --ff-only origin main
```

For a simple local fast-forward merge after review, with no changes on remote `main` since the feature branch started:

```sh
git switch main
git pull --ff-only origin main
git merge --ff-only feat/your-change
git push origin main
```

If fast-forward fails, use the pull request to resolve the divergence; do not force-push `main`. The self-service review branch is `feat/dwd-self-service`. Production application code remains on `main` until review/merge.

### Separate Supabase migration release

**Vercel builds never run migrations.** They only check environment configuration and build the workspaces. Previews use the existing DWD backend credentials, so authenticated preview actions write to that backend. `/demo` is local-only and does not touch it.

1. Create the migration with the Supabase CLI. Implement and review it locally, keeping changes compatible with the currently deployed app.
2. Run `npm test` to apply _all_ migrations in timestamp order to an isolated Docker database. The test runner never uses hosted database credentials. Do not run the fixture SQL suites against production; the older suite assumes an empty database.
3. Lint the local schema, review RLS, grants, transaction boundaries, and data preservation. Regenerate database types from the migrated test database.
4. Confirm the target is DWD (`kdplbebaotvgcvjggacz`), review a suitable backup/restore path for the change, and inspect remote migration history.
5. Execute a deliberate dry run and inspect the exact SQL/version. Use `--skip-vault` to avoid changing unrelated secret configuration. Do not include seeds or roles.

```sh
npx supabase@2.116.0 migration list --linked
npx supabase@2.116.0 db push --linked --skip-vault --dry-run
# Only after the dry run and SQL review:
npx supabase@2.116.0 db push --linked --skip-vault
npx supabase@2.116.0 migration list --linked
```

6. Verify the new schema and security advisors without inserting production test accounts. Review the Preview and merge the application code to `main`.

The self-service migration is `20260906204749_self_service_onboarding.sql`: empty plans, invite retry recovery, a finished-history index, and private account support requests. It preserves existing RLS and drink/water idempotency rules. Alcohol logged before switching to water-only can still sync against its archived plan; existing confirmation and post-end rules still apply. No product records are deleted.

Migrations are released once, independently of previews. Never add `supabase db push`, migration SQL, or a database password to a Vercel build command. Roll back application code through Vercel if needed; keep compatible additive schema changes and use a reviewed forward migration for database corrections.

## Notification and history handoff release

The initial handoff validated `20260907211443_dwd_notifications_history_plans_and_profiles.sql` locally. It and the verification corrections were applied to the dedicated hosted DWD project on September 15; see the release record below. Do not edit or reorder an applied migration.

The app has a persistent in-app notification inbox without push. Background push requires the following configuration. Only the public VAPID key belongs in the browser environment:

| Variable                           | Where it belongs                                         | Purpose                                               |
| ---------------------------------- | -------------------------------------------------------- | ----------------------------------------------------- |
| `NEXT_PUBLIC_DWD_VAPID_PUBLIC_KEY` | Vercel and browser build                                 | Public key used by the browser subscription request   |
| `DWD_VAPID_PUBLIC_KEY`             | Supabase Edge Function secret                            | Push signing public key                               |
| `DWD_VAPID_PRIVATE_KEY`            | Supabase Edge Function secret                            | Push signing private key; never expose to the browser |
| `DWD_VAPID_SUBJECT`                | Supabase Edge Function secret                            | `mailto:` or HTTPS contact for the VAPID identity     |
| `DWD_PUSH_DISPATCH_SECRET`         | Supabase Edge Function secret and scheduler secret store | Shared secret for the dispatch invocation             |

Generate one VAPID key pair for the DWD environment and use the same public key in the browser and function configuration. Set the public value in Vercel as `NEXT_PUBLIC_DWD_VAPID_PUBLIC_KEY`; set the private values with the Supabase CLI secret command. The function receives `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` from the Supabase runtime. Deploy the worker with:

```sh
supabase functions deploy dispatch-notifications --no-verify-jwt
supabase secrets set DWD_VAPID_PUBLIC_KEY=... DWD_VAPID_PRIVATE_KEY=... DWD_VAPID_SUBJECT=mailto:ops@example.test DWD_PUSH_DISPATCH_SECRET=...
```

Schedule `dispatch-notifications` from a server scheduler once the function and secrets are verified. Supabase's `pg_cron` plus `pg_net` can invoke it every minute; keep `DWD_PUSH_DISPATCH_SECRET` in Supabase Vault or the scheduler's server-only secret store rather than writing it into a committed SQL file. A Vercel Cron invocation is also valid if it sends the same header from a server-only route. The worker claims jobs with a bounded batch, uses durable delivery rows for retries, and treats 404/410 push endpoints as invalid. Do not call it from a browser.

To disable push, remove the public VAPID key from the web environment, disable or delete the scheduler, and leave account preferences available. In-app events and foreground reminders continue to work. To roll back application code, deploy the previous compatible build; keep the additive tables and use a forward migration for corrections. Do not drop notification tables while any released build may still call their RPCs.

The service worker does not cache authenticated responses. Its payload contains a generic title/body, a same-origin deep link, and no drink history. Push delivery depends on HTTPS, an active service worker, a granted device permission, an account subscription, and the configured worker. On iOS/iPadOS, Web Push is supported for Home Screen web apps from iOS/iPadOS 16.4; Safari's ordinary tab behavior is different. See [WebKit's Web Push guidance](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) and the [MDN Push API reference](https://developer.mozilla.org/en-US/docs/Web/API/Push_API). Keep the in-app inbox as the supported fallback for unsupported or denied browsers.

For subsequent environments, run `npm run test:db`, review RLS and migration SQL, apply the migrations with a dry run, deploy the app and function, configure push secrets, and activate the scheduler. Verify the in-app flows and real-device delivery separately. The September 15 release below completes hosted database and worker setup for localhost testing.

## Verification corrections, September 8 and 14

Apply `20260908065428_dwd_verification_fixes.sql` after the handoff migration and before deploying the corrected app and dispatch function. This migration fixes plan-reached logging with reminders enabled, scopes foreground reminder generation to the authenticated account, suppresses obsolete end reminders, and adds worker leases and attempt-aware acknowledgements. The worker and database must be released together: completion now includes `p_attempt`.

The active night and Account inbox refresh while visible and on reconnect/focus. Opening the inbox generates that account's due reminders even when Web Push is unconfigured. Push still requires the server scheduler; disabling its scheduler does not disable the foreground inbox. Night snapshots also reconcile every 15 seconds while visible to recover missed Realtime invalidations.

The dispatch function claims ten jobs per invocation, sends five concurrently with ten-second transport timeouts, and uses two-minute database leases. An expired lease can be reclaimed; stale attempt acknowledgements are ignored. Delivery is at least once, not exactly once: response loss after a successful push can cause a retry. Stable event notification tags replace the same displayed event. Expired subscriptions, disabled preferences, changed end times, departed members, and ended nights are checked again before delivery.

Only the supported FCM, Mozilla, Apple and Windows push-service hosts are contacted; arbitrary subscription endpoints cannot turn the worker into an HTTP proxy. The service worker verifies the event against the current authenticated account via `/api/notifications/push` before including its text or night link, with no-store requests and a five-second timeout. Stale, malformed, or unverifiable pushes display only a generic DWD update linking to Account. This preserves privacy across account switches while honoring `userVisibleOnly`: Safari can revoke subscriptions that silently discard pushes. A push already accepted by a provider cannot reliably be recalled; queued obsolete jobs are filtered before dispatch. Real-device background behavior still requires verification. [WebKit user-visible push requirement](https://webkit.org/blog/12945/meet-web-push/).

Run the Edge Function checks separately from Next.js, since the root TypeScript/lint configuration excludes Deno functions:

```sh
deno check --config supabase/functions/dispatch-notifications/deno.json supabase/functions/dispatch-notifications/index.ts
deno test --config supabase/functions/dispatch-notifications/deno.json supabase/functions/dispatch-notifications/handler_test.ts
```

Runtime dependencies are pinned in the function imports and its Deno lockfile. The September 8–14 regression checks used isolated PostgreSQL and the separate local `dwd-e2e` stack. Hosted activation followed on September 15.

Notification settings check the current account's registered device subscription, rather than equating browser permission with working push. Setup can retry after provider/registration failure; users can turn off delivery on this device independently of in-app categories. Unsupported and denied permission states have no repeated permission prompt. Failed preference loads show a retry error instead of editable defaults.

The night inbox is expandable, shows an unread count and newest update, and protects read acknowledgements from overlapping refreshes. Account keeps the full recent list. Checkboxes use the shared touch-target style, night controls use consistent links/icons, and the install tip appears on Home so it cannot cover Account settings. Light and dark screenshots are captured by `tests/e2e/handoff.spec.ts` under `.tmp/ui-review/`.
